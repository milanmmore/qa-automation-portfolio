Purpose and outcomes

UI testing validates that the interface renders and behaves correctly so users can reliably complete tasks across browsers and devices. The goal is predictable, accessible, and visually consistent experiences that hold up under real-world conditions.

  • Outcome: Catch regressions early, reduce production incidents, and increase confidence in releases.
  • Portfolio value: Show strategy, execution, and measurable impact—code, CI runs, and reports that a reviewer can verify.
Smoke run: < 3 min Flake rate: < 2% Accessibility: AA baseline

Testing types and scope

Functional

  • Controls: Buttons, inputs, selects, modals, and form validation.
  • Navigation: Routing, breadcrumbs, and back/forward history.
  • Error states: Inline errors, toasts, and retry flows.

Visual and layout

  • Rendering: Component alignment, spacing, and responsive breakpoints.
  • Diffs: Optional pixel-diff checks for critical pages.

Cross-browser and device

  • Browsers: Chromium, Firefox, WebKit.
  • Viewports: Desktop, tablet, and mobile profiles.

Accessibility basics

  • Semantics: Roles, labels, names, and alt text.
  • Keyboard: Focus order and key interactions.

Step-by-step process

  1. Requirements and risk: Map user journeys, acceptance criteria, and prioritize high-impact flows.
  2. Scenario design: Cover happy paths, edge cases, and error states with deterministic data.
  3. Author tests: Use resilient selectors, auto-wait expectations, and minimal sleeps.
  4. Execute locally and CI: Run headed/headless, capture screenshots and traces on failure.
  5. Regress and report: Validate fixes, run focused and full suites, publish reports.
  6. Improve continuously: Refactor helpers, harden selectors, and add accessibility/visual checks where valuable.

Tip: Keep test data close to tests via fixtures and factories, and isolate slow or flaky dependencies with mocks for reliability.

Tools and patterns

Core capabilities

  • Browser automation: Parallel runs, auto-waiting, and rich locator APIs.
  • Visual checks: Pixel-diff or snapshot baselines for key screens.
  • Accessibility: Automated checks plus manual keyboard/focus sweeps.

Selector strategy

  • Accessible locators: Roles, labels, and names for stability.
  • Data test IDs: Use sparingly for non-semantic components.
  • Avoid brittle CSS: Don’t couple tests to presentational selectors.

Sample UI test (Playwright)

import { test, expect } from '@playwright/test';

test.describe('Todos', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/');
  });

  test('adds and completes a todo', async ({ page }) => {
    await page.getByLabel('New todo').fill('Buy milk');
    await page.getByRole('button', { name: 'Add' }).click();

    const list = page.getByRole('list', { name: 'Todo list' });
    const item = list.getByRole('listitem').filter({ hasText: 'Buy milk' });
    await expect(item).toBeVisible();

    await item.getByRole('checkbox').check();
    await page.getByRole('button', { name: 'Completed' }).click();
    await expect(item).toBeVisible();
  });

  test('filters active todos', async ({ page }) => {
    await page.getByLabel('New todo').fill('Read book');
    await page.getByRole('button', { name: 'Add' }).click();
    await page.getByRole('button', { name: 'Active' }).click();
    const list = page.getByRole('list', { name: 'Todo list' });
    await expect(list.getByRole('listitem').filter({ hasText: 'Read book' })).toBeVisible();
  });
});

Network mocking example

test('mocks items endpoint', async ({ page }) => {
  await page.route('**/api/items', async route => {
    await route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify([{ id: 1, name: 'Mock item' }]),
    });
  });
  await page.goto('/items');
  await expect(page.getByText('Mock item')).toBeVisible();
});

Project setup

  • Structure: ui-tests/e2e/ for specs, ui-tests/fixtures/ for data, ui-tests/utils/ for helpers.
  • Config: Base URL, browser projects, retries, reporters, and test artifacts on failure.
  • Helpers: Auth fixtures, stable selectors, and network routes for deterministic runs.
// playwright.config.ts (example)
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  use: { baseURL: 'http://localhost:3000' },
  reporter: [['html']],
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
  ],
});

CI and reporting

  • Parallel matrix: Run multiple browsers and shard tests for speed.
  • Artifacts: Publish HTML reports, screenshots, videos, and traces.
  • Failure triage: Auto-attach logs, label flaky tests, and link issues to runs.
# Example GitHub Actions snippet
name: ui-tests
on: [push, pull_request]
jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --reporter=html
      - uses: actions/upload-artifact@v4
        with:
          name: ui-test-report
          path: playwright-report

Metrics and quality signals

  • Pass rate: Percentage of green runs; track per project and suite.
  • Flake rate: Percentage of tests that pass on retry; aim to reduce steadily.
  • Execution time: Average duration for smoke and full suites; optimize bottlenecks.
  • Detection and fix time: Mean time to failure detection and resolution.

Tip: Display trends over time in README or GitHub Pages to showcase reliability improvements.

Portfolio checklist

  • Scope: Document covered flows and prioritization rationale.
  • Standards: Selector strategy, accessibility minimums, and visual testing policy.
  • Setup: Install steps, environment variables, data seeding, and run commands.
  • CI: Pipeline config, browser matrix, artifacts, and triage process.
  • Quality signals: Definitions and links to reports or dashboards.
  • Demo: Example app or public target with scripts to launch locally.
